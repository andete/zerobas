## 2. Item 1 — the knife R-LS4 never had

### 2.1 Why D-LPTVERB's K7 was unsound, precisely

K7 routed `LPOS` through an existing byte-domain arm of the `ev_ff_ck*` chain
(`basic/expr.asm`). That chain runs **before** `flt_int_result`, and its arms
call `get_byte_arg`, which re-coerces **FAC**. So the cut does not add a range
test to a body — it changes how the argument is **consumed**, and the knifed
build is broken past the intended cut. Its own survivors said so:
`lps-arg1` = **195** and `lps-init` = **243**, garbage rather than columns
(§6.7.3). *A knife whose survivors return nonsense is not measuring the claim it
names.*

### 2.2 The cut site that cannot have that fault

`ev_ff_arg` finishes the argument at `ev_ff_ckdone`: `pop bc` restores the
selector, `call flt_int_result` forces the value to int16 in **DE**, and only
then does the selector dispatch reach `ev_ff_lpos`. At that instant the argument
is **fully consumed** and DE holds it. A test on DE, inserted at the top of
`ev_ff_lpos`, therefore cannot change consumption — which is the single property
K7 lacked. Both knives below cut there, and **the check that they cut soundly is
that their named survivors still return real columns (3 / 10 / 14), not that
their targets went red.**

### 2.3 The row R-LS4 was missing, added and MEASURED BEFORE the knives

R-LS4 reads *"no domain check — not even for a negative or an **out-of-byte**
value"*, and its evidence was `LPOS(1)`, `LPOS(255)`, `LPOS(-1)`. **255 is IN
byte range.** `lps-argover` (`LPOS(300)`) is the case that is int16, positive and
outside 0..255. Measured on both references, **before** anything was cut:
**`0`** on each. R-LS4 stands, now with evidence for each of its clauses, and the
`lps-` battery goes 10 rows → 11.

## 3. Item 3 — the empty-directory arm

### 3.1 The fixture, and why it is EMPTY rather than ABSENT

`python3 tools/make_test_dsk.py --empty` → `disk/empty720.dsk`: the same 720 KB
FAT12 geometry, the same boot sector, both FAT copies valid, and **no files**, so
the walk's first `ld a,(hl) / or a` on root entry 0 ends it. No volume label
either — a label entry is skipped by the walk's `$18` attribute filter and would
put a second variable in a row whose subject is *"the walk emitted nothing"*.

🔴 **Three dispositions print nothing or an error and are otherwise
indistinguishable:** "the directory is empty", "no file matched the filespec"
(R-LF6), and "there is no disk". The fixture separates the first from the third
by being **mountable and writable**, and `lfl-emptyctl` is the row that proves it
on the machine under test rather than in this paragraph.

### 3.2 The rows

| row | readout | fixture | CF-3300 | zb at `152cdaa` |
|---|---|---|---|---|
| `lfl-emptyctl` — `10 REM` / `SAVE"CTL.BAS"` / `FILES` | screen | empty, **private copy** | `CTL     .BAS` | `CTL     .BAS` ✅ |
| `lfl-emptyf` — `FILES` | screen | empty | `File not found` | **`<nothing>`** 🔴 |
| `lfl-emptyp` — `LFILES` | printer log | empty | `<nothing printed>` | `<nothing printed>` |
| `lfl-emptypb` — `LFILES` | screen | empty | `File not found` | **`<nothing>`** 🔴 |

⚠️ `lfl-emptyp` **agrees on both sides and is blind to the rule** — R-LF4's
message goes to the screen through `raise_error`, not through the listing's sink,
so an empty printer log is what a correct build *and* a build with no
empty-directory disposition both produce. It is kept because "the listing did not
leak onto the printer" is a real half of R-LF7, and `lfl-emptypb` is the half
that can see the message. Same shape as `lfl-none`/`lfl-noneb`.

### 3.3 The change

`sub/dirverb.asm`, `tnt_files`'s seed. Today:

```
                ld      a,(FILES_HASPAT)        ; 3 B
                xor     1                       ; 2 B
                ld      (DISKOP_STATUS),a       ; 3 B
```

The `xor` exists only to seed a **bare** listing at "ok", which is what makes an
empty directory silent. R-LF7 says that is wrong, so the seed becomes
unconditional:

```
                xor     a                       ; 1 B
                ld      (DISKOP_STATUS),a       ; 3 B
```

**−4 B of sub page 1.** Nothing else moves: `FILES_HASPAT` is still read per
entry for the filespec filter, `df_do_emit` still sets STATUS=1 on the first
entry emitted, and the filespec rows are bit-identical either way (HASPAT=1 →
`xor 1` → 0 → the same 0 the new code writes).

⇒ a disk whose directory holds only deleted or volume-label entries now takes the
same arm. That is the same disposition — *the walk emitted nothing* — and it is
stated rather than measured; no fixture here has such a directory.

| **K-EMPTY** | restore the `FILES_HASPAT / xor 1` seed | `lfl-emptyf`, `lfl-emptypb` → `<nothing>` | `lfl-emptyctl` (a file exists on that image), `lfl-emptyp` (the blind row — empty log either way), `lfl-none`, `lfl-noneb`, `lfl-nonef` (a filespec seeds 0 under **both** codes), `lfl-all`, `lfl-wild`, `lfl-sink`, `lfl-ctlf`, `lfl-ctlp` |

## 4. Item 2 — `do_kill`'s no-match, and the filed fix that was wrong

R-DK1: the CF-3300 answers **`File not found`**. zerobas answers `load error`.
`basic/files.asm`'s own line reads `jp z,load_error ; nothing matched -> File
not found`, so the comment was right and has been since Phase 2.

### 4.1 🔴 "The fix is 0 B (`jp z,df_notfound`)" is FALSE, and the reason is a conflation

The filed remedy is a jump-target swap, which is indeed 0 B. It is also wrong,
and a knife is not needed to see it — the call graph is enough:

* `tnt_kill` (`sub/dirverb.asm`) derives `DISKOP_STATUS` **solely** from its
  deleted-any flag `C`;
* `C` stays 0 whenever `fat_delete` returns Cy=1 on its *first* call;
* and `fat_delete` (`basic/fat-delete-body.inc`) documents its own return as
  **`Cy = 1 not found / mount / I-O error`** — it calls `fat_mount` itself.

So `STATUS = 0` today means **three** things, and `jp z,df_notfound` would
re-point all three: a disk-offline `KILL` would start raising a *trappable*
ERR 53 `File not found`, on no reading at all. That is precisely the move this
residual was filed to prevent, one disposition over
([[filed-justification-is-a-claim]] — a filed justification is a claim, including
when the filing is this project's own).

`FILES`/`LFILES` already separate exactly these three (D-LFILES: STATUS 0 =
nothing matched, 1 = ok, 2 = mount / DSKIO error, with `tf_ioerr` writing the 2).
`KILL` is made to match, which is a structural convergence and not a new idea.

### 4.2 The change

**`sub/dirverb.asm`, `tnt_kill`** — mount first, and take the existing error
tail:

```
tnt_kill:       call    fat_mount               ; +3 B
                jp      c,tf_ioerr              ; +3 B  -> STATUS = 2
                ld      c,0
                …unchanged…
```

`fat_delete`'s own `fat_mount` stays; a second mount of a mounted volume re-reads
the BPB and is idempotent. **+6 B of sub page 1.**

**`basic/files.asm`, `do_kill`'s tail** — the three-way dispatch `do_files`
already has:

```
                ld      a,(DISKOP_STATUS)
                or      a
                jp      z,df_notfound           ; 0 -> ERR 53 "File not found"
                dec     a                       ; +1 B
                jp      nz,load_error           ; +3 B   2 -> mount / DSKIO error
                jp      exec_stmt
```

**+4 B of main page 1** (194 → 190; the co-mapped budget 197 → 193).

⚠️ **What is still conflated, said out loud:** an I-O error inside `fat_delete`
*after* the mount succeeded and *before* anything was deleted still returns C=0
and reads as "nothing matched". Separating that needs a status out of
`fat_delete` itself, which is a primitive-layer change this slice does not make.
The mount half is the half the fix would otherwise have broken.

### 4.3 The pin moves in the same commit as the code

`probes/disk/disk_probe_fat_error_disposition.py` pins all eight rows to one
global `WANT = "load error"`. `kill-missing` becomes `File not found`, so `WANT`
becomes **per case**. The other seven are untouched and stay `load error` — they
are the quarantined divergence, and nothing here measured them.

### 4.4 The knives

Subject: `probes/basic/basic_probe_dskmsg.py --gate --sides cf3300,zb`, invoked
directly, plus `probes/disk/disk_probe_fat_error_disposition.py`. **Run twice.**
