# `GETDPB` ($4016, disk ROM) — the drive parameter block for a media byte

> **Spec:** DRAFT 1 (2026-11-22), two measured rounds, no review yet. Measured on the VG-8020 with an
> NMS 1200 disk interface.

## Summary

`GETDPB` is one of the disk ROM's published entries, called in the disk interface's slot (CALSLT,
the slot from DRVTBL at $FB22). Given the media byte in B and a DPB address in HL, it fills the drive
parameter block a DOS needs for that format: the 18 bytes after the DPB's drive byte. It works from
the media byte ALONE -- it does not read the disk -- and each standard format ($F8 to $FF) has its own
block. It returns the carry clear.

zerobas's disk ROM reads the disk instead, and fills the block of the format on the disk whatever B
says (D-GETDPBMEDIA).

## The specification

References: the Philips VG-8020 with an NMS 1200 disk interface (row `D`). Ours: zerobas's disk build.
The VG-8020 alone (row `N`) has no disk ROM, so nothing is called there.

**Evidence.** **[XE1 n]** / **[XE2 n]**: step `n` of the XDENT1 probe, run 1
([`scratchpad/XDENT1_run1.out`](../../scratchpad/XDENT1_run1.out)), or of XDENT2, run 1
([`scratchpad/XDENT2_run1.out`](../../scratchpad/XDENT2_run1.out)). `probes/bios/spec/xdent1.asm` and
`xdent2.asm` document the frame (XDSK1's H.STKE cartridge, drive A holding the generated empty 720 KB
disk) and the 30-byte record: A, F, B, C, D, E, H, L, the interrupt state after, and the 21 bytes from
HL ($A400, filled with $E5 before each call). Every case enters with A 0 (drive A), F 0, DE 0, HL
$A400, interrupts off; B and C as the probe lists.
