## Summary

`GETDPB` is one of the disk ROM's published entries, called in the disk interface's slot (CALSLT,
the slot from DRVTBL at $FB22). Given the media byte in B and a DPB address in HL, it fills the drive
parameter block a DOS needs for that format: the 18 bytes after the DPB's drive byte. It works from
the media byte in B ALONE -- C plays no part, and it does not read the disk -- with the standard
format's block for each measured media byte ($F8, $F9, $FA, $FC, $FD, $FE, $FF; $FA's block equals
$FF's but for the media byte, as $FD's equals $F8's). It returns the carry clear and A = 2 x (B - $F8).

zerobas's disk ROM reads the disk instead, and fills the block of the format on the disk whatever B
says; with no disk it fails (A 2, carry set) (D-GETDPBMEDIA).

**A third interface.** Which media bytes GETDPB takes is the interface's: the NMS 8250's built-in drive (rows
N, scratchpad/XDENT1_run3.out to XDENT7_run3.out) writes the same 18 bytes for $F8, $F9 and $FA, and REFUSES $FC .. $FF with the
carry set and nothing written (R-GD-REFUSE), where the NMS 1200 takes all eight; its A and HL index its own table.

## The specification

References: the Philips VG-8020 with an NMS 1200 disk interface (row `D`). Ours: zerobas's disk build.
The VG-8020 alone (row `N`) has no disk ROM, so nothing is called there.

**Evidence.** **[XE1 n]** / **[XE2 n]** / **[XE3 n]** / **[XE5 n]**: step `n` of the XDENT1 probe, run 1

([`scratchpad/XDENT3_run1.out`](../../scratchpad/XDENT3_run1.out)), or of XDENT5, run 1, with drive A
