# `DSKCHG` ($4013, disk ROM) — was the disk changed

> **Spec:** DRAFT 1 (2026-11-22), two measured rounds, no review yet. Measured on the VG-8020 with an
> NMS 1200 disk interface.

## Summary

`DSKCHG` is one of the disk ROM's published entries, called in the disk interface's slot (CALSLT, the
slot from DRVTBL at $FB22): has the disk in drive A changed? Within about a second of the last disk
access the answer is B 1, unchanged, and nothing else happens. After 3 s or more idle, and at the
first call after start-up, the answer is B 0, unknown: the call reads the disk and fills the DPB at HL
for the disk's media byte, as [GETDPB](GETDPB.md) does, returning that media byte in A. B $FF
(changed) needs a disk swap, not measured here.

zerobas's disk ROM answers by the same clock and fills the same block, but returns other registers on
the B 0 path (D-DSKCHGREGS).

## The specification

References: the Philips VG-8020 with an NMS 1200 disk interface (row `D`). Ours: zerobas's disk build.
The VG-8020 alone (row `N`) has no disk ROM.

**Evidence.** **[XE1 n]** / **[XE2 n]**: step `n` of the XDENT1 probe, run 1
([`scratchpad/XDENT1_run1.out`](../../scratchpad/XDENT1_run1.out)), or of XDENT2, run 1
([`scratchpad/XDENT2_run1.out`](../../scratchpad/XDENT2_run1.out)). `probes/bios/spec/xdent1.asm` and
`xdent2.asm` document the frame and the 30-byte record (as on [GETDPB's page](GETDPB.md)). Every
DSKCHG enters with A 0 (drive A), F 0, B 0, C $F9, DE 0, HL $A400 (filled with $E5), interrupts off.
XDENT2 waits between calls with interrupts on (EI / HALT, 50 timer interrupts a second): its steps
are DSKCHG, DSKCHG, ~1 s, DSKCHG, ~3 s, DSKCHG, ~10 s, DSKCHG. XDENT1's two DSKCHG come right after
five GETDPB calls.
