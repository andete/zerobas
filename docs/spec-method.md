# How a BIOS / BDOS call's page is made — the spec method

Developer documentation. It describes HOW the per-call pages in [docs/bios/](bios/index.md)
and [docs/bdos/](bdos/CONOUT.md) are written, reviewed and finished. The pages themselves are
user documentation and the specification at once (Joost, 2026-11-17: one page per call, no
separate spec tree).

The method was piloted on the BDOS console output, CONOUT / STROUT / DIRIO, on 2026-11-17. It
comes from the *elephant and goldfish* model ([egm.dev](https://egm.dev/)):
- an author who knows everything (the **elephant**, the long-running session) drafts;
- reviewers who know nothing but the page (**goldfish**, fresh agents) report what is missing,
  unsupported or ambiguous.

## 1. Where things go

- **One page per call:** `docs/bios/<NAME>.md` (main BIOS) or `docs/bdos/<NAME>.md` (MSX-DOS
  BDOS).
- **Shared facts of a region live once, in its concept page** (`docs/concepts/`). The region for
  each call, and its page, are in [docs/bios/index.md](bios/index.md), generated by
  `tools/bios_spec_index.py`. Typical shared facts: the screen state and cursor cells, the slot
  conventions, the PSG registers, work-area cells several calls read. A fact in two places
  drifts, so a call page LINKS to the concept page, never restates it.
- **Evidence** — probe programs, captures and tables — lives in `probes/` and `scratchpad/`; pages
  cite it.
- **What a call touches** (cells, VDP registers, ports, interrupt state) is ONE table:
  [docs/bios/shared-state.md](bios/shared-state.md), compiled from the published interface. A call's
  page links its row; a measurement that contradicts a row corrects the row. Its "couplings" list is
  read before fixing a region: which other regions share the state a fix touches.
- **Per-call STATE never goes on a shared page.** A concept or base page does not repeat a call's
  status, its differences or its TODO items (Joost, 2026-11-17, on the base page listing CHPUT's).
  The generated index shows them, read from each call's own page, so they cannot drift.
- **This method** lives here and nowhere else.

## 2. The page

The keyword pages' skeleton ([docs/keywords/LOCATE.md](keywords/LOCATE.md)), with the contract
sections the specification needs:

1. **Title:** `` `NAME` ($addr) — what it does``.
2. **`> **Spec:** <state>` line** — `DRAFT n`, `REVIEWED n` or `FINAL`, plus a dated note naming
   the reference(s) measured. The index reads this line; a page without it fails
   `bios-spec-index-check`.
3. **Summary** — plain prose for a reader, no evidence tags.
4. **The specification** — Interface (registers in / out, flags), Behaviour (the rules), each
   sentence carrying an evidence tag (§3).
5. **Differences from the reference** — zerobas against the reference, with the TODO item that
   fixes each.
6. **Open (not measured)** — every `[A]`.
7. **Related pages, Tests that cover it.**

## 3. Evidence tags and the one rule that matters

Every sentence of the specification carries one tag:
- **[M ...]** names a measured row or case in an evidence table (each page defines its tables'
  short tags, e.g. `[XM n]`);
- **[P]** a published interface document's statement;
- **[A]** assumed: not measured.

**A sentence the author DERIVED — summarised, generalised, "therefore" — still needs a row or an
[A].** In the pilot's third review every factual error sat in such a sentence ("zerobas's counts
are one higher throughout", "the BDOS reads the cell at each byte"); none sat in a cited row.

Clean room (unchanged, see [allowed-sources.md](allowed-sources.md)): registers, RAM, VRAM, I/O ports and slot
state are readable. A reference ROM byte, a hook target or a disassembly never is.

## 3a. Executable rules — a page cannot say more than its data (Joost, 2026-11-17)

Every BEHAVIOUR rule a page states is also a check over its measured cases. Writing tables by hand
from thousands of cases failed the same way twice on CHPUT: over-generalising ("a byte from 64
up", true only for 64–95), mis-summarising (LINTTB's orientation), and leaving out behaviour
that was measured (the wraps, the scroll, the edges).

- **The rules file.** Each page with a measured case set gets `probes/bios/spec/<name>_rules.py`.
  It defines `PAGE`, `cases()` (the reference's and zerobas's measured cases, each with the
  page's citation id) and `RULES`. A rule pairs `select` (which cases it speaks about) with
  `expect` (what it says about them), plus the sentence the page shows.
- **The checker,** `tools/spec_rules.py`, reports three things:
  - **a rule FALSE on any reference case** it selects: the sentence is wrong, so fix the rule,
    never the data;
  - **zerobas's failures:** its differences, which the page's Differences section maps to TODO
    items;
  - **the cases no rule covers:** measured but not stated. It is a count, and the page's open
    list must account for every one.
- **Coverage is FIELD-LEVEL.** Each case group declares its recorded outputs (`OUTPUTS`). While a
  check runs, the case records which outputs, and which list entries, it reads. An output no check
  reads is uncovered. A case merely SELECTED by a rule that reads none of its behaviour does not
  count, and neither does a check that reads one entry of a list its sentence talks about in full.
  (CHPUT's first "0 uncovered" was hollow for 33 cases and 5,741 outputs; the third review found it.)
  Outputs the setup itself decides are declared in `UNREAD`, with the reason, and rendered on the
  page: accounted for, never covered.
- **A probe's setup must not use the call under test.** CHPUT rounds 2 and 3 placed the cursor with
  CHPUT's own `ESC Y`. Where the two machines' `ESC Y` differs, every case STARTED somewhere else,
  so the differences were the setup's. Set the state through other means: VRAM writes, the work-area
  cells directly. Retire the affected groups from the rules, with the reason; their data stays on file.
- **No self-relative expectations.** A check's expected values come from the REFERENCE, never from
  zerobas's own other cases. CHPUT compared each machine's "prefix + byte" with ITS OWN "byte
  alone", so a zerobas bug present in both halves was invisible (prefix + DEL; the fourth review).
  Where a machine's own state must be the baseline (the key line's labels belong to DSPFNK, not
  CHPUT), say so in the rule. Then pin the behaviour separately against probe-written markers.
- **The checker refuses a rule whose text names a rule id that does not exist** (stale references
  after a rewrite), and renders the sections in order.
- **Generate a probe's case table from the module that decodes it** (CHPUT round 5,
  `xchput5_cases.py`), so the layout cannot drift between probe and rules.
- **The page's rule tables are GENERATED** between `<!-- RULES BEGIN -->` and `<!-- RULES END -->`
  (`--write`). `make spec-rules-check` (in STATIC) fails on a false rule or a stale page. The
  Summary and the Open list stay hand-written, and short.
- **Reviewers** then read the rules and the data for what only a fresh reader finds:
  - a selector that dodges awkward cases;
  - two rules the cases cannot separate;
  - a measurement that is missing.

  "Uncovered cases" tells them where to look.
- **The test audit (§8)** takes its gate cases from these rules. They state the reference's
  behaviour, so a gate can run the probe on zerobas alone and check them.

## 4. References

- **The main BIOS:** the Philips **VG-8020** is the primary reference; tools/bios_levels.py
  measures against it. The Panasonic CF-3300 is the second.
- **The BDOS:** the CF-3300 (the disk system's reference).
- **When the references differ,** the page records both. A purely presentational split ships
  the VG-8020's value (Joost, 2026-09-04).

## 5. The loop for one call

1. **Gather.** Read the call's existing evidence: its gate rows, bios_levels's level and note,
   the probes that call it.
2. **Measure.** Prefer a MATRIX to a list:
   - every input value, from a state built so that rival rules give DIFFERENT answers;
   - "desynced": in the pilot, the count and the cursor set apart, so "unchanged" could not hide
     "follows the cursor".
   Record every output the call could plausibly touch: registers, flags, the cells, the cursor,
   VRAM.
3. **Write** the page (§2, §3).
4. **Review** (§6). Score each finding — real / already known / wrong — and answer a real one by
   MEASURING, not by arguing. Fix the page.
5. **Repeat 4** until the stopping test (§7).
6. **File each difference** as a TODO item with its 🎚️ tier. The existing loop fixes it, and its
   gate rows come from the page's cases.
7. **Audit the call's tests** once its core rule is FINAL (§8): one sharp gate case per rule; the
   rows that pin nothing are retired, with mutation evidence.

## 6. Review — depth and prompts

**Depth is adaptive** (Joost, 2026-11-17):
- Region concept pages and rich calls (CHPUT, CHGET, the slot calls...) get two reviewers per
  pass until the stopping test.
- Small calls, or a group sharing one contract (GTSTCK / GTTRIG / GTPAD), get one reviewer, and
  stop at the first pass with no finding on the core rule.
- One reviewer run costs on the order of 100k tokens.

Each reviewer is a FRESH agent that may read only the page(s) under review and the evidence files
they cite: no other repository file, no search, no runs. The two roles, verbatim:

**Implementer.** "Your role: you are the engineer who must IMPLEMENT the behaviour these pages
describe, with nothing but them. Report:
1. anything you would need that they do not say, or say ambiguously (the question you would ask,
   and why it blocks);
2. any claim its own cited data does not support (name the row and what it shows);
3. inconsistencies;
4. cases a reasonable implementation would hit that are neither specified nor listed as open.
A numbered list, most important first, one to three sentences each; no style, no praise; 'none'
for an empty category."

**Test writer.** "Your role: you must write the ACCEPTANCE TEST that decides whether an
implementation matches the reference, using only these pages. Report:
1. rules NOT pinned by any measured case, and the measurement that would pin each;
2. rules the measured cases could ALSO explain with a different rule — both rules, and the case
   that separates them;
3. citations that do not match the tables;
4. gaps in the open lists.
Same format."

For a page past its first pass, add to both: "Items the page already lists as not measured count
only if the list is wrong."

## 7. When a page is done — the stopping test

A pass is CLEAN when it finds **no rule pair the evidence cannot separate** and **no factual
error** about the call's core rule.
- After a clean pass the core rule is marked FINAL on the page. Its remaining open items stay
  `[A]` and do not hold up the fixes.
- A page whose core rule is FINAL may go to implementation.
- Findings that belong to ANOTHER call (the pilot's CHPUT questions on the CONOUT page) move to
  that call's page.

The pilot, for scale: three passes, each of two reviewers, on CONOUT:
- the "rule pairs not separated" findings went ~15 → ~11 → 0 on the core rule;
- each pass was answered by measurement: 84 → 153 cases → a 1287-case matrix.

## 8. The test audit — fewer, sharper tests (Joost, 2026-11-17: "vitally important")

A page does not replace a test: only a run notices that OUR code drifted. What a FINAL page does
is say exactly which rules a gate must pin and which case separates each rule from its rivals.
Most existing rows pin less than they appear to. The pilot's rows mostly agreed "for the wrong
reason": they started where the rival rules coincide, so ten of them proved less than one
desynced case.

The audit, once the call's core rule is FINAL:

1. **Map.** For every gate row that calls the entry (`tools/entry_table.py` names them), write
   down which of the page's rules it pins: the rule, and whether its inputs SEPARATE that rule
   from the page's rival rules. A row that cannot fail under any rival rule pins nothing.
2. **Fill.** Every rule needs at least one gate case that separates it. The page's own cases
   (its matrix) are the source; turn them into gate rows, with the page's measured reference
   values as the expected values, so spec and test are one table and cannot drift apart. A rule
   with no separating case in a gate is a TODO item, not a page footnote.
3. **Prove the cut.** "This row is redundant" is a claim like any other, and is answered by
   measuring. Break the rule in OUR ROM and confirm that the REMAINING gate rows still go red
   without the row to be retired (`scratchpad/gate_blindness_sweep.py`; the battery is the
   denominator). Each retirement names its mutation and the row that caught it.
4. **Retire** only proven-redundant rows, in a commit of their own: what went, which rule each
   pinned, and which row now catches it.
5. **Record** the result on the page's *Tests that cover it* section, as one line per rule: the
   rule → the gate case that pins it.

The page's open list (`[A]`) is then exactly where tests are missing, so "how many tests do we
need" becomes a count rather than a feeling.

Why it matters: the FULL gate's hour is mostly emulator boots, scenario after scenario. A call
whose rules are each pinned by one matrix row group, run on zerobas against the page's stored
reference values, needs no scenario suites of its own. Rows are retired only with mutation
evidence, never because a page "covers" them.
