omsx_repl: name a missing capture, and stop 8 emulators sharing one settings.xml

THE FLAKE HAD A CAUSE AND THE HARNESS WAS THROWING IT AWAY. Six of seven full
batteries on 2026-08-25 recovered a "FLAKE (green on retry)". Every one was a
single `<NO CAPTURE>` on a random row and a random side -- and not one carried a
diagnostic line, because openMSX's stdout and stderr went to DEVNULL and its
exit status was used only as a liveness boolean and then discarded.

`<NO CAPTURE>` is the same string for at least four different events: the stall
watchdog fired, the abscap backstop fired, openMSX died on its own, or the guest
genuinely wedged. Which one it was decides what to do next, and the fourth is a
REAL DEFECT that `tools/run_gates.py` would retry into green and label a flake.

_why_missing() now spends the evidence the run already held -- which watchdog if
either, the exit status or signal, the elapsed wall, how many lines the run
wrote, and openMSX's own last words. It prints only when a capture is actually
missing.

ON THE VERY FIRST BATTERY THAT HAD IT, IT NAMED THE CAUSE:

  openMSX terminated ON ITS OWN (exit 1) after 0s wall, before its scheduled
  capture; the run wrote 0 line(s).  emulator said: Uncaught exception: Failed
  to parser settings file 'settings.xml': systemID doesn't match

Every openMSX process reads ~/.openMSX/share/settings.xml at start and REWRITES
it at exit. In a parallel battery a starting process reads a file another is
mid-rewrite of, refuses to boot, and exits 1 in under a second. So each run now
gets its own copy via openMSX's own `-setting` flag. Side effect, and a good
one: probe runs no longer write the user's openMSX settings.

MEASURED, because counting flakes across batteries is not causal evidence.
scratchpad/flake/repro.py drives the mechanism instead of waiting for it -- a
writer tears a settings file non-atomically, exactly as openMSX does on exit,
while starts race it. SHARED 35/40 starts failed (87.5%); ISOLATED 0/40. Both
arms run against a COPY; the user's own file is never touched.

Draft 1 of that reproducer came back 0/96 on BOTH arms and is kept in the
docstring: it started processes in synchronised waves, so they all read at one
moment and all rewrote at another, and the dangerous overlap is a START against
somebody else's EXIT. A falsification with no teeth is a claim about the
experiment before it is one about the code.

probes/lib/omsx_missing_teeth.py + `make omsx-diag-teeth`: the standing
falsification, five cases -- a GREEN control that must print NOTHING, and four
forced failures (stall watchdog, abscap backstop, a CRASH, a graceful SIGTERM)
that must each be named DIFFERENTLY. It exists because _why_missing is a
failure-formatting branch: no healthy run executes it, so nothing else in the
tree can notice it rot. DELIBERATELY NOT in `make gates` -- two cases signal
`openmsx` by name and would hit a neighbour in a parallel battery, so it refuses
to start while any openmsx is running.

Its first three drafts went red for their own reasons and the code was correct
every time: `-machine No_Such_Machine` never reaches the launch (omsx_preflight
refuses it first, correctly); ZEROBAS_OMSX_ABSCAP is defeated by
`max(timeout, ...)`; and `pkill` defaults to SIGTERM, which openMSX HANDLES and
exits 0 on -- so "exited CLEANLY (0)" was the right answer to the wrong
question. SIGTERM and SIGKILL are now separate cases, because a graceful stop is
not a crash and must not read as one.

make gates: 37/37 green with ZERO flakes and zero retries -- the first fully
clean battery of the day. That is n=1 and is not the evidence; the reproducer
and the captured message are. ROM hashes 41b8c4ed ae796ccb 7d27b871, unchanged.
